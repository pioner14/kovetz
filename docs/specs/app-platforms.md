# spec://app/platforms

## Поддерживаемые платформы

Текущая Flutter-бета в `app/` выпускается для Linux x86-64, Android и Windows x86-64. Интерфейс доступен на русском и английском. Обработка архивов выполняется локально.

## Сохранение результата

На Linux и Windows используется системный диалог сохранения с защитой входных файлов от перезаписи и записью пары `.jwlibrary` + `.report.txt` через временные файлы и откатом при ошибке. На Android папка пары выбирается через `ACTION_OPEN_DOCUMENT_TREE`; существующие документы сохраняются, новому результату при необходимости добавляется числовой суффикс. Отмена диалога возвращает пользователя к готовому результату.

## Разрешение конфликтов

Один главный бэкап задаёт порядок избранного и приоритет позиций закладок. Все уникальные элементы избранного объединяются без ограничения десятью. На публикацию сохраняется до десяти закладок; переполнение подробно перечислено в TXT. Для заметок с одним GUID выбирается самая свежая версия LastModified (по умолчанию) либо версия главного бэкапа; разные GUID сохраняются отдельно. Для ответов используется главный бэкап (по умолчанию) либо дата исходного бэкапа. Подробности предупреждений и очередь закладок хранятся во временной SQLite, отчёты записываются построчно. Наследуемый JSON и служебные карты ID пока требуют памяти пропорционально входным данным.

## Совместимость входных данных

Программа принимает проверенные структуры схем 5, 8, 14 и 16. Выход всегда имеет схему 16, user_version=16 и databaseName=userData.db. Существуют два варианта схемы 16: прежний и вариант JW Library на GRDB (таблица grdb_migrations v9–v13). Если хотя бы один вход записан GRDB-версией, результат получает её схему дословно; иначе — прежнюю. На устройстве восстановились оба варианта. Все входные базы открываются только для чтения и нормализуются в собственную схему перед объединением; входные SQL-триггеры не выполняются при исправлении связей. В схеме 5 Type=0 привязки TagMap обозначает Location, Type=1 — Note. При отсутствии Note.Created берётся исходный LastModified.

Ошибки страниц SQLite, контрольной суммы и неизвестные структуры сообщаются пользователю. Пропущенные внешние ссылки обрабатываются в рабочих копиях. Читаемые заметки сохраняются, неустановленные привязки перечисляются в отчёте. Недостающие медиа можно восстановить из остальных выбранных архивов по совпадающей SHA-256. Локальные числовые ID разных устройств не считаются одинаковой сущностью.

Архив результата содержит только userData.db, manifest.json и медиафайлы — как бэкап самой JW Library: архив с любыми другими файлами JW Library отклоняет («Сохранённые данные повреждены», проверено на устройстве 21.11.2026). Поэтому копии исходных бэкапов в результат не вкладываются (исходники не изменяются), а все непереносимые строки и альтернативные версии перечислены в TXT-отчёте. Машинный отчёт формата 2 создаётся рядом с архивом только для диагностики. История проблем импортируется из результатов версий до 0.4.2, где отчёт лежал внутри архива (формат 1 и 2); у новых результатов её переноса нет. Альтернативные тексты заметок и ответов сохраняются в TXT с происхождением и выбором версии. Интерфейс показывает постоянное предупреждение и позволяет сохранить результат.

Старые плейлисты схемы 8, для которых пока не подтверждена семантика миграции, сохраняются исходными строками и файлами в отчёте и вложенном архиве. Слияние прочего содержимого продолжается. Для каждой публикации сохраняются до десяти закладок в SQLite, оставшиеся закладки сохраняются в отчёте.

## Сборки и проверка

Workflow `.github/workflows/app-beta.yml` собирает Linux, Android и Windows. Анализ Dart и сквозные тесты ядра выполняются на Linux и Windows. Проверка готового архива включает контрольную сумму базы и целостность SQLite. Восстановление результата в JW Library проверяется на Windows или Android.

## Проверка структур и графов, версия 0.3.2

Сопоставление выделений включает метаданные и весь набор BlockRange. При одном GUID выбирается целая версия по Version и приоритету входа; остальные различающиеся графы сохраняются в conflictVersions. Порядок и полные исходные графы современных плейлистов также сохраняются при расхождении. Семантическая идентичность медиа в элементе определяется SHA-256, сохраняя действительные повторы.

Известные структурные контракты включают столбцы, affinity/NOT NULL, PK, уникальные индексы (с выражениями и partial), FK и CHECK. Контракты проверяются до чтения пользовательских строк и повторно на границе нормализации. Файл tool/schema_contracts.json содержит проверенные схемы без пользовательских данных; schema_contracts.dart воспроизводимо генерируется скриптом разработчика. Неизвестный вариант требует отдельного изучения и регрессионных фикстур. Проверки структуры не заменяют восстановление на устройстве с JW Library.

## Проверка обновлений, версия 0.6.0

Единственное обращение приложения в интернет — запрос списка релизов репозитория на GitHub (`api.github.com`). Он выполняется по кнопке «Проверить обновления» или раз в сутки при запуске, если пользователь включил автоматическую проверку (по умолчанию выключена). В запросе нет сведений о пользователе, устройстве и файлах. Принимаются релизы, у которых есть файлы `kovetz-…`; черновики пропускаются, пре-релизы учитываются. Установка выполняется вручную: ссылка на файл платформы открывается в браузере (при неудаче копируется). Разрешение INTERNET добавлено в Android-манифест только для этой функции.

## Руководство пользователя

Данные руководства хранятся в `docs/user-guide/guide.<lang>.json`. Из них `app/tool/build_guide_md.dart` генерирует Markdown, а `app/tool/build_guide_site.dart` собирает статический сайт в `docs/site`. Workflow `.github/workflows/pages.yml` публикует сайт на GitHub Pages. Приложение открывает ссылку на полное руководство в браузере, чтобы сохранить небольшой размер сборки. Снимки экрана создаются с помощью `app/tool/screenshots_test.dart` и `app/tool/make_help_images.sh` только на синтетических данных.
