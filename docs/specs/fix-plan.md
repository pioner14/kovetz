# План исправлений после аудита 0.3.2

> Состояние на 20.11.2026 (версия 0.4.0): этапы 1, 3–8 выполнены, кроме пунктов, отмеченных «осталось». Этап 2 — за Николаем.

Основание: `dist/audit-0.3.2-2026-11-20.md`. Стратегия — исправлять по этапам, не переписывая проект. Каждый этап — отдельный коммит (или серия), после каждого обязательно запускаются `flutter analyze` и `flutter test`. Поведение слияния меняется только вместе с регрессионным тестом.

## Этап 1. Сохранность кода и репозитория (без изменений кода)
1. Дополнить `.gitignore`: бинарники и архивы в корне (`/*.exe`, `/*.zip`), служебные файлы IDE и Gradle внутри `app/`.
2. Ветка `flutter-app`, коммиты по порядку: `.gitignore` → `legacy/` (перенос Python) → `app/` → `docs/`, workflow, README.
3. Перед каждым коммитом проверять `git status`: в индекс не должны попасть ни одного `.jwlibrary`, `.report.txt`, `.exe` или `.zip`.
4. Push ветки и PR — только с разрешения, чтобы автосборка проверила Linux, Windows и Android.
5. Убрать из корня личные бэкапы, старые результаты и бинарники (место — по решению Николая).

## Этап 2. Проверка на устройстве (делает Николай)
Сделать отдельный бэкап в JW Library → восстановить результат слияния → проверить заметки, выделения, закладки, плейлисты → сделать повторный экспорт. Результат записать в `docs/specs/audit-progress.txt` (п. 8).

## Этап 3. Ресурсы и размер результата
1. Бюджет распаковки: суммарный размер, число элементов, размер одного элемента; проверяется до записи по центральному каталогу и во время записи по фактическим байтам.
2. Лимит размера `recovery-report.json` из прошлого результата.
3. Вложения `recovery-sources/` из прошлого результата не считать медиа: переносить один раз, дедуплицировать по SHA-256. Заменено в 0.4.3: вложения в архив не кладутся вообще — JW Library их отклоняет.
4. Тесты: архив сверх бюджета отклоняется с понятной ошибкой; повторное слияние не увеличивает число вложений.

## Этап 4. Диагностика и мягкая обработка
1. Причина ошибки сохраняется (тип исключения, этап) и показывается пользователю без личных данных; «io» — только для настоящих ошибок ввода-вывода.
2. Повреждённый `recovery-report.json` → отдельная понятная ошибка.
3. Неоднозначная Location не останавливает слияние: запись уходит в отчёт.
4. Тесты на каждый случай.

## Этап 5. Рефакторинг (поведение не меняется, тесты — страховка)
1. Общие SQLite-хелперы в `lib/src/sqlite_utils.dart`.
2. `merge.dart` → `archive_reader`, `media`, `sanitizer`, мерджеры по сущностям, `recovery_store`, `report_text` (текст отчёта — отдельный слой).
3. Коды ошибок — enum вместо строк.
4. `main.dart` → экран, контроллер состояния, `ExportService`, виджеты.
5. Переводы интерфейса — gen-l10n (ARB). **Осталось.**

## Этап 6. Эффективность
Объединить однотипные запросы (N+1), кешировать SHA-256 медиа, сохранять версии записей только при расхождении, уменьшить число промежуточных копий на диске. Замер до и после на корпусе в `.work/audit/`.

**Осталось:** ленивое сохранение версий (около 70 % времени слияния) и сокращение промежуточных копий на диске.

2. Release-подпись: конфиг читает `key.properties` вне git; **осталось** создать ключ и задать секреты CI (Николай).
