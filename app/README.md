# Объединение резервных копий JW Library

Flutter-приложение для Linux, Android и Windows. Оно объединяет выбранные файлы `.jwlibrary` в одну резервную копию. Обработка выполняется локально. Интерфейс доступен на русском и английском.

## Что умеет приложение

- **Объединить бэкапы** — три шага (файлы, правила, результат); результат и TXT-отчёт сохраняются парой файлов.
- **Экспорт заметок** — заметки с тегами из любого бэкапа или результата слияния: Markdown для Obsidian (папка на компьютере, ZIP на Android) и PDF-книга по тегам с оглавлением. Шрифты встроены, русский и армянский текст печатаются без пустых квадратов.
- **Обновления** — проверка новой версии вручную или раз в сутки при запуске (по умолчанию выключено). Приложение запрашивает у GitHub только список релизов репозитория; свои файлы и сведения об устройстве оно не отправляет. Скачивание и установка выполняются вами из браузера.

## Совместимость бэкапов

Проверены реальные резервные копии 2019–2026 годов со схемами SQLite 5, 8, 14 и 16. Приложение автоматически переносит их в формат 16, даже когда все выбранные бэкапы старые. Заметки, выделения, теги, избранное, закладки, ответы и современные плейлисты объединяются локально. Перед объединением можно выбрать главный бэкап (по умолчанию самый свежий). Избранное сохраняется целиком, сначала в порядке главного бэкапа. Его закладки занимают свои позиции, остальные заполняют свободные места. Для заметок с одинаковым GUID можно выбрать свежую версию по LastModified или приоритет главного бэкапа. Разные GUID сохраняются отдельными заметками. При различии текстов заметок и ответов все варианты сохраняются в TXT и машинном отчёте с источником и отметкой выбранной версии. Одинаковая закладка в другой позиции объединяется с исходной. Для ответов доступны приоритет главного бэкапа (по умолчанию) и выбор по дате бэкапа.

Выделения выбираются целиком: больший `UserMark.Version`, при равенстве — приоритет основного бэкапа. `Version` используется как числовой приоритет, а не как доказанная дата изменения. Диапазоны разных вариантов не смешиваются. Отличающиеся цвета, места и диапазоны сохраняются в отчёте вместе с исходной версией.

Современные плейлисты объединяются в основном порядке с добавлением дополнительных элементов. Намеренные повторы сохраняются, включая повторные ссылки на одну запись в старых схемах. Сопоставление одинаковых элементов выполняется отдельно внутри каждого плейлиста. Изменённые маркеры остаются отдельными элементами; одинаковое содержимое медиа под разными именами не создаёт новый элемент. Отличающиеся исходные графы и порядок плейлистов сохраняются в отчёте для сравнения.

Проверка входной структуры использует известные варианты таблиц из синтетических фикстур, предоставленных экспортов 2019–2026 годов и собственной выходной схемы. Проверяются столбцы и их affinity, NOT NULL, первичные и уникальные ключи, внешние связи, CHECK-условия и согласованность `user_version` с манифестом. Неизвестная структура останавливает объединение с указанием таблицы; содержимое пустой таблицы тоже не обходится молча. Пробелы, комментарии и кавычки идентификаторов не меняют результат проверки. Описания в `tool/schema_contracts.json` содержат только структуру, без пользовательских записей; `tool/generate_schema_contracts.py` — необязательный инструмент разработчика, Python для работы приложения не требуется.

При обнаружении неполных связей приложение сохраняет доступные данные и показывает постоянное предупреждение. Недостающие медиа ищутся в остальных выбранных файлах по SHA-256. При сохранении рядом с результатом создаётся UTF-8 файл `.report.txt`: выбранные правила, число сохранённых объектов и подробности о неперенесённых записях с причинами. Закладки, которым не хватило позиций, перечислены с названиями и публикациями. Архив результата содержит только то, что принимает JW Library: базу, manifest и медиафайлы. Любые лишние файлы внутри архива JW Library считает повреждением, поэтому копии исходных бэкапов и машинный отчёт в архив не кладутся. Исходные бэкапы не изменяются — сохраните их. История проблем читается из результатов версий до 0.4.2, где отчёт лежал внутри архива; если старый отчёт не позволяет однозначно установить происхождение записей, неоднозначные записи сохраняются отдельно. Сам формат базы JW Library остаётся 16.

Для старых плейлистов схемы 8 точное соответствие современной структуре пока не подтверждено. Их исходные строки, изображения тегов и файлы сохраняются в отчёте и вложенном исходнике. В публикации допускается десять позиций закладок. При заполнении всех позиций дополнительные закладки также сохраняются в отчёте.

Linux-версия объединяет файлы независимо от JW Library. Результат можно перенести на устройство с JW Library. Восстановление в самой JW Library следует проверить на тестовом устройстве.

## Проверка и сборка

Готовые сборки находятся в `dist/` в корне репозитория. Локальный Flutter SDK, инструменты и временные файлы находятся в `.work/`.

Установите [Flutter 3.50.0](https://docs.flutter.dev/install/archive) и инструменты своей платформы. Выполняйте команды из каталога `app/`.

```sh
flutter doctor -v
flutter pub get
flutter analyze
flutter test
```

Постоянные тесты находятся в `app/test/`. `merge_test.dart` проверяет миграции и обычные сценарии объединения; `annotation_graph_test.dart` — целостность выделений, медиа, маркеры, порядок и повторы плейлистов; `schema_contract_test.dart` — проверку неизвестных структур; `security_test.dart` — опасные ZIP-пути и входные SQL-триггеры; `data_preservation_test.dart` — сохранность альтернатив, закладки и повторную историю; `report_history_test.dart` — происхождение альтернатив и совместимость истории отчётов; `export_test.dart` — запись пары, откат ошибок и защиту исходников от перезаписи; `property_test.dart` — инварианты слияния на случайных бэкапах (ни один GUID не теряется, правила выбора, идемпотентность); `cleanup_test.dart` — удаление брошенных временных копий; `rules_widget_test.dart` — правила объединения на русском и английском при разной ширине экрана. Общие синтетические фикстуры вынесены в `test/support/merge_fixtures.dart`. Личные архивы для этого набора не требуются.

Регрессионные тесты требуют правильного поведения. Исправлены десять выявленных аудитом падений: входные триггеры, сохранность альтернатив, идентичность закладок и повторная история. Эти проверки активны и не используют skip/xfail. Перечень закрытых проверок и оставшихся ограничений — в `test/KNOWN_FAILURES.txt`. Все входные базы, включая схему 16, открываются только для чтения и копируются в собственную схему перед восстановлением связей.

| Платформа | Инструменты и команда |
| --- | --- |
| Linux | Clang, CMake, Ninja, pkg-config и заголовочные файлы GTK 3. Запуск: `flutter run -d linux`. Сборка: `flutter build linux --release`. |
| Windows | Visual Studio с компонентом **Desktop development with C++**. Сборка: `flutter build windows --release`. |
| Android | Android SDK и JDK 21. Тестовый APK: `flutter build apk --debug`. Release APK: `flutter build apk --release` (подпись — ниже). |

Замер скорости на собственных бэкапах (папка вне git): `dart run tool/benchmark.dart <папка> all`.

### Подпись Android

Release-сборка подписывается ключом из `app/android/key.properties` (файл и ключ в git не попадают):

```properties
storeFile=/полный/путь/kovetz-release.jks
storePassword=…
keyAlias=kovetz
keyPassword=…
```

Ключ создаётся один раз командой `keytool -genkeypair -v -keystore kovetz-release.jks -keyalg RSA -keysize 4096 -validity 10000 -alias kovetz`. Храните его и пароли в надёжном месте: без них нельзя выпустить обновление, которое установится поверх. Без `key.properties` release-сборка подписывается отладочным ключом.

В CI release APK собирается, если в секретах репозитория заданы `ANDROID_KEYSTORE_BASE64` (ключ в base64), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` и `ANDROID_KEY_PASSWORD`; иначе собирается тестовый APK.

## Сборки для бета-тестирования

В GitHub откройте **Actions → Flutter beta builds → Run workflow**. Для ручного запуска workflow должен присутствовать в основной ветке. Он также запускается при изменении приложения или workflow в pull request. Сборки появляются в разделе **Artifacts** конкретного запуска и хранятся 14 дней. Доступ к скачиванию определяется видимостью репозитория и правами пользователя.

- **Linux:** распакуйте архив `kovetz-linux-x64.tar.gz` и запустите `./bundle/kovetz`. Оставьте рядом каталоги `data` и `lib`. Сборка рассчитана на x86-64 и собирается на Ubuntu 24.04.
- **Windows:** распакуйте артефакт и запустите EXE из распакованной папки. DLL и каталог `data` должны лежать рядом. На компьютере тестировщика может потребоваться [Microsoft Visual C++ Redistributable](https://learn.microsoft.com/cpp/windows/latest-supported-vc-redist).
- **Android:** установите APK `kovetz-android.apk` на тестовое устройство, например командой `adb install kovetz-android.apk`. Тестовый APK подписывается отладочным ключом. Если ключ предыдущей сборки отличается, ее нужно удалить перед установкой.

Workflow сохраняет артефакты без публикации в GitHub Releases или Google Play.

На Android проверьте выбор нескольких архивов и сохранение бэкапа и TXT-отчёта через выбор папки. На Windows и Android восстановите результат в JW Library на тестовых данных.

## Выпуск версии на GitHub

Приложение ищет обновления среди релизов репозитория и принимает только те, у которых есть файлы `kovetz-…` (старые релизы Python-версии без файлов игнорируются).

1. Поднимите `version:` в `app/pubspec.yaml` и `appVersion`/`appBuild` в `app/lib/app_info.dart` (тест сверяет их).
2. Закоммитьте и отправьте изменения в `main`.
3. Поставьте тег и отправьте его: `git tag v0.6.1 && git push origin v0.6.1`. Тег со знаком «-» (`v0.6.1-beta`) публикуется как пре-релиз.
4. Workflow `.github/workflows/release.yml` проверит, что тег совпадает с версией, соберёт Linux, Windows и Android, подпишет APK постоянным ключом (секреты из раздела «Подпись Android») и создаст релиз с файлами `kovetz-<версия>-android-arm64.apk`, `-linux-x64.tar.gz`, `-windows-x64.zip` и `SHA256SUMS.txt`. Без ключа подписи Android-сборка прерывается: APK, подписанный отладочным ключом, не публикуется.
